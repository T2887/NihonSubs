## 一、这是什么

把 PC 版**兼容模式**的流水线搬到手机上：视频/音频 → 日文转写 → 中文翻译 → SRT 字幕，全程离线。

和 PC 版的关系：**不是移植代码，是重新实现**。手机上跑不了 PyTorch / faster-whisper，所以换了技术栈。
**改安卓版时不需要看 PC 版代码** —— 两者只共享「翻译 prompt 文本」和「字幕风格的约定」。

| | PC 版兼容模式 | 安卓版 |
|---|---|---|
| 语音识别 | SenseVoiceSmall（PyTorch） | SenseVoiceSmall **ONNX int8** |
| 翻译 | Hy-MT2-1.8B Q4_K_M | 同款模型（`hy.gguf`） |
| 提音频 | ffmpeg | ffmpeg（arm64 静态版） |
| 翻译服务 | llama-server | llama-server（同一份源码） |
| 字幕整理 | Rust | Rust（复用逻辑） |

> ⚠️ **安卓版用的不是 faster-whisper**，所以 PC 全量模式的很多修复（clip_timestamps 分段、幻觉拦截等）**不适用**，别直接照搬。

## 四、运行时架构（这是最难懂的部分）

### 4.1 为什么二进制要改名成 `lib*.so`

Android 10+ 起，app 私有目录里的文件**不能执行**（SELinux `untrusted_app`，实测 `Permission denied`）。
只有 APK 的 `lib/<abi>/` 目录（运行时 `getApplicationInfo().nativeLibraryDir`）允许 exec。

所以 ffmpeg / llama-server / sherpa / 自写程序**全部改名成 `libXXX.so`** 放进 `jniLibs/arm64-v8a/`。

| 文件 | 实际是什么 | 大小 |
|---|---|---|
| `libffmpeg.so` | ffmpeg 静态版 | 15.7 MB |
| `libllamaserver.so` | llama-server | 11.7 MB |
| `libsherpaoffline.so` | sherpa-onnx 离线识别 | 2.3 MB |
| `libasmrmobile.so` | 自写的翻译+写字幕 | 378 KB |
| `libonnxruntime.so` | ONNX Runtime | 22.2 MB |
| `libsherpa-onnx-{c,cxx}-api.so` | sherpa 依赖 | — |
| `libvadasr.so` | VAD+ASR（旧方案残留，见 6.2） | 2.4 MB |

### 4.2 流水线（`app/src/main/assets/run.sh`）

```
输入媒体文件
  ↓ [1] ffmpeg → 16kHz 单声道 wav
        例外：App 已用系统 MediaCodec 解好的 .wav 直接跳过这步
  ↓ [2] llama-server 起本地翻译服务（127.0.0.1:18081，带 --metrics）
        ★ 旧版写的是「已有进程就复用（pidof llama-server）」，但那个判据恒为空，
          复用从来没生效过 —— 见 4.5。现已改为 llama_pid() + /health 双判据
  ↓ [3] ffmpeg 按【固定 20 秒】切段 → sherpa-onnx 分批识别
        每批 24 段，批间模型重载约 1.7s
  ↓ [4] libasmrmobile.so 逐句调翻译服务，写 .chs.srt
```

### 4.3 三个关键实测约束（别再踩）

**① 必须按固定 20 秒切段，不能整段 VAD**
ASMR 里大量喘息/耳语/环境音，Silero VAD 全判成语音，整段 VAD 会"一直不断句"。
实测 1.5 小时素材，阈值 0.5/0.6/0.7、min-silence 0.1/0.2、max-speech 5/10 都试过，
**只切出 45~55 段**，字幕漏掉大段内容。固定 20 秒切段后每段都有输出。

**② 必须按最高频率动态挑大核，不能硬编码 `taskset 0F0`**
`0F0` 只适合「4 小核在 cpu0-3、4 大核在 cpu4-7」的布局（天玑 1000+ 就是）。
换到 1+3+4 / 2+2+4 或编号顺序不同的机器，`0F0` 可能正好绑到小核 ——
**实测小核跑 llama 比大核慢 27 倍**。
现在按 `cpufreq/cpuinfo_max_freq` 降序取前 4 个核，读不到频率就不绑核。

**③ 识别必须分批，一次全塞会 OOM**
一次把 276 个 wav 交给 sherpa-onnx 会被 OOM killer 杀掉（日志出现 `Killed`）。
每批 24 段，换内存平稳。

### 4.4 其他坑

- **toybox 的 taskset 只认纯十六进制**（不带 `0x`），`taskset 0xf0` 会报 bad mask
- **Android 的 mksh 不支持 `/dev/tcp`**，判服务在不在要用 HTTP 探活（`curl /health`），
  没 curl 才退回 grep 日志的 `listening on`。**别用 `pidof llama-server`** —— 见 4.5
- **`/health` 判据必须看状态码，不能只看 curl 退出码**：模型加载期间服务已 bind 端口、
  返回 **503**，而 `curl` 退出码仍是 0 → 假就绪（实测「等了 1s 就报就绪」，
  真正能翻译要到 25 秒后）。现在判据是 `%{http_code}` 等于 200
- **`run.sh` 末尾不能无条件 `rm -f "$WAV"`**：.wav 输入时 `WAV="$IN"`，
  那是用户交进来的原始文件 —— 旧代码**处理完就把源文件删了**，见 4.6
- **判断服务就绪要 grep 日志里的 "listening on"**，不能加 `--log-verbosity 0`（那样一行日志都没有）
- sherpa 把文件名标题打到 **stderr**、JSON 打到 **stdout**，所以 `run.sh` 手写 `#SEG_OFFSET` 批次起始段号，`asmr_mobile` 用它乘段长换算绝对时间

### 4.5 ★ 进程名坑：`pidof llama-server` 恒为空（2026-11-10 定位）

二进制为了拿到 exec 权限改名成 `libllamaserver.so`（见 4.1），于是内核里的
`comm` 是 `libllamaserver.`（15 字符截断）、`cmdline` basename 是 `libllamaserver.so`
—— **两者都不等于 `llama-server`**。实测：

```
pidof llama-server      -> (空)
pidof libllamaserver.so -> 28271      ← 这才是能用的
```

**后果（一直没被发现的性能损失）**：旧 `run.sh` 用 `if ! pidof llama-server` 判复用，
条件恒真 → **每个文件都重新 nohup 起一个服务**，白加载一次 1.1 GB 模型（30~90 秒）；
新进程 `bind 18081` 失败静默退出，真正在服务的还是上一个老进程。
91 分钟那种多文件任务，每个文件都多付一次加载。

**现在的写法**：`llama_pid()`（先 `pidof libllamaserver.so`，再退回 `llama-server`）
+ `server_alive()`（`curl /health`，无 curl 则 grep 日志）双判据，并把**真正在服务**的
pid 写进 `_llama.pid`。

### 4.6 ★ 曾删用户源文件（2026-11-10 修复，别再改回去）

`run.sh` 里 .wav 走「系统已解好，直接用」分支：`WAV="$IN"`。
而脚本末尾原本是无条件的：

```sh
rm -f "$WAV" "$TXT"      # ← WAV 此刻等于用户的原始 .wav
```

`cleanup()`（出错路径）里一直有防护 `[ "$WAV" != "$IN" ]`，**只有成功路径漏了**。
实测后果：把 `asmr01.wav` 放进 input 目录，跑完字幕后**源文件从目录里消失**。
手机上被删的是副本还算轻的 —— 用户直接选自己手机里的音频，就是删他的文件。

现在成功路径复用同一个判断；另外 `start_llama` 等待超时（120 秒）会 `cleanup; exit 1`，
不再硬跑到 [4/4] 让整片字幕静默回退成日文原文。

### 4.7 进度卡的「运行状态」行（2026-11-10 新增）

跑任务时每 2 秒刷一行，形如：

```
运行状态　模型 写9.4/读16 t/s  4.0核  大核2.2-2.2G
```

三路数据源（`MainActivity.java` 的 `collectStats()`，`statsLoop()` 每 2 秒一轮）：

| 显示项 | 来源 | 说明 |
|---|---|---|
| 写 x t/s | `/metrics` 的 `tokens_predicted_total` | 生成(decode)吞吐，counter 在 2 秒窗口做差 |
| 读 x t/s | `/metrics` 的 `prompt_tokens_total` | prefill 吞吐 |
| x.x核 | `/proc/<pid>/stat` 的 utime+stime | 进程实际占用核数，pid 读自 `_llama.pid` |
| 大核x-xG | `scaling_cur_freq`（cpu4-7） | 能直接看出**有没有被热降频** |

为什么是这三路而不是「整机 CPU%」：**App 读不到 `/proc/stat`、
`/proc/loadavg`、`/proc/uptime`（SELinux 全部 Permission denied，实测）**，整机占用率拿不到。
但 App 能读同 uid 子进程的 `/proc/<pid>/stat`（llama-server 是 App fork 的），
所以用「进程占了几核」替代「整机几成」。

**实测数值（K30U，clip90 + asmr01）**：写 9~11 t/s、读 13~22 t/s、4.0 核
（正好等于 `-t 4`，可用来验证绑核有没有跑偏），大核在 2.6 / 2.245 / 1.75 GHz 之间跳 ——
**1.75 就是热降频现场**。

**热降频的量化影响（同一 ASR 文本、同一服务，冷机 vs 持续负载后）**：

| 状态 | 大核频率 | decode | prefill |
|---|---|---|---|
| 冷机 | 2.60 GHz | 9.6 tok/s | 18.1 tok/s |
| 热机 | 1.27 GHz | 7.1 tok/s | 10.4 tok/s |

频率降 51%，decode 只降 26%、prefill 降 43% ——
**decode 受内存带宽限制（对核频不敏感），prefill 受算力限制（接近线性）**。
所以任何「提速 X%」的对比必须同热机状态交替测，否则结论会被热漂移污染
（本次就吃过这个亏：v7 的 clip90 全流程 35s vs v5 的 21s，差在热机状态，不是回归）。

排查用：`Log.i("AsmrStats", ...)` 会把同一行文本 + 三路各自的成功情况打进 logcat，
因为 2 秒一次的 `setText` 让窗口永不 idle，`uiautomator dump` 会卡住，只能用 logcat 采样：

```
adb logcat -s AsmrStats:I
```

### 4.8 碎片合并 + 翻译重试（2026-11-10 v7，Rust 侧）

**背景数据**：同一段素材（巧可 01，2.5 分钟），安卓断句出 48 条（字数中位 4），
PC 全量模式只 14 条（字数中位 13）。`GAP_SPLIT=0.55` 在 ASMR 素材上把
「感冒？还是翘课？」切成「风」+「还是偷懒呢」这种碎片。

**改动 1 · 翻译前合并**（`native/asmr_mobile/src/main.rs` 的 `merge_segs()`）：
相邻条满足「间隔≤0.30s 且 并后≤6.5s 且 并后≤40 字 且（前条非强句末结尾 或 前条≤6 字）」并成一条。
实测 48→23、36→15，接近 PC 密度。

**受控 A/B**（同一 ASR 文本、同一常驻服务、merge/nomerge 交替两轮抵消热漂移）：

| 模式 | 条数 | 翻译耗时 | Δgen（总生成 token） |
|---|---|---|---|
| merge | 23 | 21.2 / 22.0 s | 164 / 166 |
| nomerge | 48 | 25.6 / 25.7 s | 182 / 183 |

**提速约 14~17%，且总生成 token 反而少 10%**（合并后模型不再为碎片重复补语境）。
调试开关：`ASMR_NO_MERGE=1` 环境变量可临时关掉合并。

**已知局限（诚实记录）**：
- 合并救不了识别层丢字。实测「風邪」（感冒）被 SenseVoice 切成「風」+1.7 秒后的「そ」，
  「邪」整个丢了 → 合并后译文「今天怎么这么风呢」不通顺。这是 ASR 缺陷，不是合并缺陷。
- 偶尔把两句语义完整的话并成一条（前条≤6 字且带句末标点时）。权衡后接受：
  ASMR 素材里这种「谢谢。」多半本来就是被切碎的半句。

**改动 2 · 翻译重试**（`translate_retry()`）：
照 PC 版 v1.28.5 的教训 —— 安卓原来失败一次就把**日文原文静默写进 SRT**，用户不知道哪条没译。
现在重试 3 次（第 2、3 次 temperature 抬到 0.3 跳出复读），仍失败则标 `[未译]` 前缀，
并在末尾汇总报错条数。

**被否掉的方向（实测数据）**：llama-server 的 `-np 4` 多 slot 并发 decode 在这台机器
**毫无收益**（np=1 并发 14.08s vs np=4 并发 13.53s，差 3.9% 在噪声内；np=4 串行反而慢 42%）。
decode 吞吐被内存带宽锁死，客户端再怎么并发都排同一条队。别再往这个方向投入。

### 4.9 ★ 识别层选型实测（2026-11-10，六个模型，别再重复做）

同一段 14 秒素材（含「風邪ですか」关键句）加官方中文字幕素材（`1_前言`，195.5 秒），
在 K30U 上逐个真机实测。这一节花的十几个小时换来的结论，直接决定要不要换识别层。

| 模型 | 体积 | RTF | 保健室 | 風邪 | 标点 | 时间戳 | 结论 |
|---|---|---|---|---|---|---|---|
| SenseVoice int8（现状） | 229 MB | 0.056 | ✗ ホチへ室 | ✗ かせ | 无 | ✓ | 可用，默认 |
| whisper base（ggml） | 141 MB | 0.42 | ✗ 保陣術 | ✗ カーセ | ✓ | ✓ | 慢 8 倍且不准 |
| zipformer-ja（ReazonSpeech） | 153 MB | **0.064** | **✓** | **✓** | 无 | ✓ | 词级最准，但会整段漏 |
| Qwen3-ASR 0.6B int8（sherpa） | 983 MB | 0.375 | ✗ 補欠生 | ✗ 風情 | ✓ | **✗ 完全没有** | 结构性不可用 |
| Kotoba-Whisper v2.2 q4_0（ggml） | 444 MB | 3.82 | ✓ | ✗ 風 | ✓ | ✓ | 慢 60 倍，不可用 |
| Qwen3-ASR 1.7B | — | — | — | — | — | — | sherpa 格式里不存在（HF/GitHub 全 404） |

**为什么 Qwen3-ASR 不可用**：sherpa 的 qwen3 实现不输出时间戳
（`csrc/offline-recognizer-qwen3-asr-impl.cc` 里 `timestamp` 出现 0 次，JSON 的 `timestamps` 恒为 `[]`），
而本 App 的 SRT 时间轴全靠 token 时间戳 —— 除非另配强制对齐器，否则接不进来。
另外 ModelScope 的 `Qwen3-ASR-0.6B.tar.bz2` 解压出来是 `model_int8.qint8`（私有量化格式），sherpa 不认；
能用的只有 `HatiSkoll28/sherpa-onnx-qwen3-asr-int8-0.6B`（conv_frontend + encoder + decoder + tokenizer 目录）。
**Kotoba 的坑**：`Pomni/kotoba-whisper-v2.2-ggml-allquants` 的 q4_0 是 444324515 字节，
encode 一次固定付 30 秒 mel 窗口的开销，14 秒音频也要 52 秒，1.5 小时素材要 5.7 小时 —— 别试了。

**官方中文字幕素材实测**（`1_前言`，195.5 秒，官方 57 条）：

| 识别层 | 段数 | 官方时间覆盖率 | 覆盖不足一半的官方条数 | 全流程总耗时 |
|---|---|---|---|---|
| SenseVoice int8 | 37 | **98.4%** | 1 | 47 秒 |
| zipformer-ja | 30 | 85.3% | 8 | 45 秒 |

**★ zipformer-ja 的问题：会整段跳过音频（根因已查清，PC 侧复现确认）**。
在「20s + 前后各 1.5s」的窗口里有 3 处整块没识别：官方 40/41（20.65-23.40）、
官方 54（1:23.03-1:26.05）、官方 80-83（2:43.82-2:55.25 —— 整整 11 秒对话消失），
我们的 SRT 从那段时间直接跳过去。实测特征（`_w8.sh`~`_w13.sh` 那批实验）：
- **确定性**：同一音频 `--num-threads` 1/2/4 各跑一遍、再重跑，输出完全一样 → 不是线程竞态。
- **不只看长度**：23 秒窗口 `-ss 158.5` 只认出最后 5 秒；同样的 23 秒 `-ss 100` 全对。
- **前置静音有时能救**：`-ss 158.5 -t 23` 前面垫 2.0s 静音 → 全对；垫 0.5s → 更差（只剩「はい」）。
- **换起点也能救**：`-ss 162 -t 12` 全对；`-ss 160 -t 16` 只认出「ありがとうございます」。
- （整段 195 秒一次喂已在 PC 侧复现并定位根因，见下一段）

**根因（2026-11-10 晚，PC 侧 `sherpa-onnx` + `off1.wav`(195.5s) 复现确认）**：
对 zipformer-ja 的 RNN-T，一个**缺少可靠上文的冷启动窗口**会整体丢失段首、甚至只吐一个感叹词。
- **完全确定**：同一输入连续跑输出完全一致（`r151_1/2/3`、`r158_1/2/3` 各 3 遍都稳），不是随机、不是线程竞态。
- **前置静音存在临界阈值**：158-181.5s 窗口前面垫 0.5s 及以下还是「はい」（2 token），垫 1.0s 及以上就整句正常（77~80 token）。
  → RNN-T 需要约 ≥1 秒真实上文才能可靠起句，冷启动区长度是关键变量。
- **换起点等价于给上文**：`-ss 162 -t 12`（已过切点、有上文）全对，`-ss 160`/`158.5` 就丢 —— 同一现象。
- **整段一次喂既不准又危险**：195s 整段喂，模型开头 186.9 秒全部静默、几乎只有末句；内存随音频长度平方增长，
  在手机上和 llama-server 同跑时实测触发 `kernel_panic,oom` 内核重启。**不要再整段喂。**

**extreme 结论：这不是 zipformer 的 bug，是 RNN-T 冷启动固有行为 + 部分区间确实没有连贯语音。**
用 `off3`(3_舔耳朵,629s) 对 zipformer-ja 与 SenseVoice **同一硬窗**交叉验证：内容密集段（0-78s/238-260s/598-620s）
两模型都完整认出；气流/低耳语段（178-200s/338-360s）两模型都空（SenseVoice 标 `<|nospeech|>`/`<|Breath|>`）。
所谓「zipformer 整段漏」除上面 3 处（20.65-23.40/1:23-1:26/2:43-2:55，旁边有真实对话被硬切点切断）外，
其余是素材在该区间本就没有连贯语音。**默认仍走 SenseVoice 不受影响；zipformer 词级更准，可经 run.sh 探测启用。**

**危险操作（别试）**：整段（>约 90s）一次性喂 sherpa 编码器，内存随长度平方增长（20s→约 200MB、195s→多 GB），
手机实测触发 `boot.reason=kernel_panic,oom` 内核重启。正常 App 20s 一窗+前后余量不会触发。

结论：换窗口边界只是「碰运气」，不算修好。**双车道融合（见 4.10）已落地为默认**；
SenseVoice 单车道仅在对齐素材另有要求时（或两套模型缺一时）回退，见下文。
zipformer-ja 下载源：`sherpa-onnx-zipformer-ja-reazonspeech-2024-08-01.tar.bz2`
（GitHub k2-fsa/sherpa-onnx releases；国内直连约 46 KB/s，走 hf-mirror 多线程直连可到 ≈2.2 MB/s），
只需 `encoder-epoch-99-avg-1.int8.onnx`(148M) + `decoder-epoch-99-avg-1.onnx`(11M) +
`joiner-epoch-99-avg-1.onnx`(10M) + `tokens.txt`，改名成 `encoder.int8.onnx / decoder.onnx / joiner.onnx`。


### 4.10 ★ 双车道融合：zipformer 主 + SenseVoice 补漏（2026-11-10 落地，app 默认）

§4.9 的两个实测事实拼出最合理方案：**zipformer 词级最准但会冷启动丢句**，
**SenseVoice 覆盖最广但字词常错**（保健室→ホチへ室）。二者在质量上互补，就做了融合：

- **主输出 = zipformer-ja**（一段 20s + 前后各 1.5s 余量的硬窗，词级准）。
- **补漏 = SenseVoice**：先跑完 zipformer 全片，扫描出「哑窗/空窗」，只对**这些窗**单独补跑
  SenseVoice，把结果按绝对时间缝合回主车道缺的洞。SenseVoice 不用全片跑（省一半识别耗电）。
- **哑窗的判据**：一个窗口里**所有段合起来的最长一句** ≤ 4 个字符（典型 = 冷启动只吐「あっ/うん」），
  或者该窗口一条段都没有（空窗）。阈值 `DUMB_WIN_MAX = 4`（off3 标定：哑窗 chars 全=2、正常最低 7、临界 4，无歧义）。
- **窗口归属定死**：窗口 i 的绝对起点 = `i*20 - 1.5`（`#SEG_OFFSET` 批次标记按**文件个数**累计，
  空窗 wav 不出 JSON 行时靠它不串位）。识别、扫描、补跑、缝合四处用的 `--seg-sec`/`--lead` 必须一致。

落地的代码（全在本会话完成并通过验证）：

| 层 | 文件 | 改了什么 |
|---|---|---|
| 融合逻辑 | `native/asmr_mobile/src/main.rs` | 新增 `Lane`/区间解析、`find_dumb_windows`、`fuse_lanes`；cli 加 `--scan`/`--backfill`/`--total-win` |
| 编排 | `app/src/main/assets/run.sh` | 模型双车道探测 + `ASR_KIND` 三态（fused/zipformer/sensevoice）+ `recognize()` + fused/单车道双路径 |
| 产物 | `jniLibs/arm64-v8a/libasmrmobile.so` | 已换成上面的 aarch64 release 构建（本次会话重编） |

**run.sh 运行期组装**（fused 分支，三段单行代码）：
1. `echo "#SEG_OFFSET 0"` 后，`recognize $ZIP_TXT zipformer $SEGDIR/seg_*.wav` 全片。
2. `$BIN_MT $ZIP_TXT /dev/null --scan $DUMB_LIST --total-win $NSEG` → 定位哑窗名单（不翻译不写 SRT）。
3. 若名单非空：逐窗 `echo "#SEG_OFFSET $WN"` + 单窗 sherpa(SenseVoice) 补跑得 `$SV_TXT`，
   再 `$BIN_MT $ZIP_TXT $OUT --backfill $SV_TXT --total-win $NSEG` 缝合。名单空则直接单车道出字（省 SV）。

**模型怎么放**（fused 需要两套齐全）：
- zipformer-ja → `models/zipformer-ja/`（encoder.int8.onnx / decoder.onnx / joiner.onnx / tokens.txt）
- SenseVoice → `models/model.int8.onnx` + `models/tokens.txt`（SV 的 tokens 固定叫 tokens.txt，放子目录和 zipformer 同名文件隔离）。
- 只放齐一套 → 单车道回退（zipformer 或 SenseVoice）；两套都不齐才报错。

**验证情况（2026-11-10 晚）**：
- Rust 侧 `cargo test`（宿主直跑）3 用例全绿：哑窗扫描含空窗、融合保留主车道并填洞、无补跑时保持单车道。
- PC-host 真二进制端到端：对真实 `_win_txt.json`（真实 zipformer 输出，8 窗）`--scan` 正确报出 4-7 为空窗，
  `--backfill` 缝合后 SRT 里 80s/100s/120s 的洞被 SenseVoice 句填上、绝对时间正确、输出 UTF-8 合法、`--no-translate` exit 0。
- 真机 zipformer 单窗冒烟：K30U 上 2 线程 23s 窗正常出 JSON（结构即 asmr_mobile 解析格式），未触发重启。
  ⚠️ **`run.sh` 的 `$THREADS` 已固定压到 2**（2026-11-10）：实测 4 线程连跑多窗会触发
  `boot.reason=kernel_panic,oom` 内核重启 —— 7.6GB 内存被 zipformer + 系统常驻 + SwapCached 一起顶穿。
  2 线程单窗稳定（RTF≈0.076）。**不要改回 4**，改了大概率复现重启。

> **为什么没做「全片 SenseVoice 跑一遍、zipformer 只在 SV 有洞时补」的反向方案**：调研+实测后你的结论是
> zipformer 的词级准确度值得做主车道，SenseVoice 只用来补 zipformer 的洞，覆盖最省。方向和实现均是拍板后落地的。

## 七、接手须知

### 改代码的入口

**界面/控制逻辑** → `MainActivity.java`（1589 行，全在一个文件里）
**流水线** → `assets/run.sh`（319 行 shell）
**翻译+写字幕** → `native/asmr_mobile/src/main.rs`（**Rust**，529 行，编译成 `libasmrmobile.so`）

> `asmr_mobile` 是个独立的 Rust bin crate（只有 `serde_json` 一个依赖），
> 用 `opt-level="z" + lto + strip` 压到 378 KB。
> 它做三件事：① 解析 sherpa 输出转成段 ② 逐句 HTTP 打 llama-server 翻译 ③ 写 SRT。
>
> **两个关键常量在 `main.rs` 顶部**：
> - `GAP_SPLIT = 0.55` —— 句末停顿超过 0.55 秒就断句（否则 20 秒一段会变成一条巨型字幕）
> - `TAIL = 0.45` —— 最后一句的尾巴时长（token 时间戳只标起点，没有终点）
>
> **翻译 prompt 抄自 PC 版**：`SYSTEM` 常量与 `light_translate.py` 的 SYSTEM 完全一致，
> 改的时候两边要同步，否则手机和电脑翻出来的风格会不一样。
>
> HTTP 是**手写的最小实现**（纯 std 的 `TcpStream`），没引 reqwest/ureq ——
> 手机上没有 TLS 需求，不想为这点功能塞依赖。改网络部分时注意这一点。
>
> ⚠️ 这句话**只适用于 `127.0.0.1` 回环**（llama-server 就在本机）。它**不构成
> 「安卓版能访问外网」的基础**：一旦要加 PC 版 10-31 那种「检查更新」（https），
> 手写 TcpStream 直接不可用，必须另找方案（Java 侧 `HttpURLConnection`，或引 rustls）。

### 三条注意事项

1. **先用真实片子跑一遍再改**。安卓的行为和 PC 差很多（没有 faster-whisper、CPU 算力差两个数量级），PC 上的「常识」在这里经常不成立。

2. **跑之前先看 `run.sh` 顶部那几段注释**。里面记的都是踩过的坑（20 秒切段、动态挑大核、分批识别），改回"更优雅"的写法会直接翻车。
   （`run.sh:12-17` 就是那段 VAD 实测记录，`SEG_SEC=20` 在第 33 行，改之前先看这两处。）

3. **测试素材在 `artifacts\`**：`clip90.mp4`（90 秒）、`ja30.wav`、`jp30.wav`、`long20.mp4`，
   还有几次跑的对照字幕 `clip90_*.srt` / `long20.chs.srt` / `test_long*.chs.srt`。
   （`downloads\` 是源码压缩包，`artifacts\` 才是模型和测试素材）

## 九、常见误解（别踩）

1. **"把 PC 版的修复同步过去"** —— PC 全量模式的核心修复依赖 faster-whisper 的
   `clip_timestamps`，安卓用 sherpa-onnx + SenseVoice，**没有这个概念**，改不了。

2. **"20 秒切段太粗暴，改成智能 VAD 更好"** —— 试过了，见第 4.3 节。
   整段 VAD 在 ASMR 素材上会"一直不断句"，漏掉大段内容。

3. **"taskset 0F0 就行"** —— 只在特定 CPU 布局成立，别的机器可能绑到小核，慢 27 倍。

4. **"二进制为什么叫 .so"** —— 不是动态库，是伪装成 .so 的可执行文件，
   因为 Android 10+ 只允许 `lib/<abi>/` 下的文件 exec。见第 4.1 节。
