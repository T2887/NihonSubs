## 2026-11-11 v1.1.8（尚未发布）

### 一、整机卡死：根因与做法

**现象**：处理 89 分钟 1080p 片子时，整机失去响应（系统弹「进程 system 没有响应」），
adb 也挂死。

**实测证据**（Redmi K30 Ultra，7.6 GB 内存）：

| 观察项 | 数值 |
|---|---|
| `libsherpaoffline.so` RSS 峰值 | 2.5 GB → 4.1 GB |
| `MemAvailable` | 0 kB |
| `SwapFree` | 645 MB → 104 kB（用尽） |
| `kswapd0` CPU | 96% |
| `iow` | 528% |
| ANR 顺序 | system_server 先倒，随后 systemui / 本 App 连环 |

**受控测量**（同一批切好的 wav，只跑识别）

| 一批段数 | 峰值 RSS |
|---|---|
| 1 段 | 461 MB |
| 3 段 | 835 MB |
| 6 段 | 1410 MB |

⇒ 基线约 280 MB，**每多喂一段就涨约 190 MB，且同一进程内不释放**。
所以「批次大小」只能缓解，不能根治；叠加 llama-server 常驻的 2.0~2.2 GB 才是致命组合。

**结论与改动**

1. 识别批次 24 → **4**（`BATCH`，可用 `ASMR_BATCH` 覆盖，上限 8）。
2. 翻译服务改成**识别全部跑完才启动**（`ensure_translator` 推迟调用）。
   识别阶段内存里只有识别模型（0.2~1.0 GB）。
3. 老版本的 `/sdcard/.../models` 一次性搬到 App 私有目录
   `/data/user/0/com.nihonsubs/files/models`（`migrateModelsIfNeeded`），
   顺带解决 FUSE + mmap 的缺页放大。
4. 推理进程加 `nice -n 10`，给系统进程让路。

**踩过的坑（务必记住）**

- 用 root 直接在 App 的 bin 目录跑 `run.sh` 会留下 **root 属主的临时文件**，
  之后 App 解压 assets 失败：`bin` 里连 `run.sh` 都没了，`.assets_vN` 标记生不出来。
  修法：`rm -rf $B/bin/_asmr_* $B/bin/_seg_*` 后 `chown -R u0_a423:u0_a423`。
- `adb install` 走 **Incremental Install** 时 assets 不一定会刷新；
  改 assets 后要确认设备上的 `run.sh` 时间戳/内容变了。
- 设备满载时 `adb` 会挂起：命令要放后台 job，别在前台等。
- `adb shell "a | b"` 在 PowerShell 里会被吃掉引号/竖线；
  一律把脚本写到本地 → `adb push` 到 `/data/local/tmp/x.sh` → `su -c "sh ..."`。

## 2026-11-11 03:40 v1.1.8（第二批：暂停 + 断点续跑 + UI 对齐）

### 一、底部按钮与「使用说明」的取舍

底部动作条从「开始处理 | 停止 | 使用说明」改成 **「开始处理 | 暂停 | 停止」三等分**，
「使用说明」移到页面标题右侧的小胶囊。原因：三个按钮各占 1/3 宽时「停止」两个字还是比
「开始处理」窄一截（曾是 WRAP_CONTENT），改成等权重后视觉才齐；而四个按钮挤一排每个只剩
约 80dp，「开始处理」四个字会缩到很难读，所以把低频的「使用说明」挪到标题栏。

### 二、暂停 = SIGSTOP 冻结，不是「停掉重来」

**需求**：处理中可以暂停，继续时不丢进度。

**做法**：`togglePause()` → `sendSignal(freeze)`，用 `/system/bin/kill -STOP / -CONT`
冻结整条进程树：
- `run.sh` 的 pid 用反射 `Process.class.getMethod("pid")` 拿；
- 真正的重活在同名 native 进程里，按 cmdline 搜 `libllamaserver.so` / `libsherpaoffline.so`
  / `libvadasr.so` / `libffmpeg.so`（复用已有的 `findPidByCmdline`）。

**为什么不能只冻 run.sh**：`sh` 只是调度器，冻了它、识别进程还在跑，进度照样前进；
反过来只冻识别进程也不行 —— sh 会以为子进程回来了继续下一批。两个一起冻才是原地暂停。
**为什么不用「停止 + 记住进度重跑」**：整段 ASR 结果在 `bin/_zip.txt` 里，但 llama 翻译
是按批流式写的，重跑要重来一整段，代价远大于冻结。

实测：暂停后 `ps` 里 `libsherpaoffline.so` 状态是 `TN`（T = stopped），界面阶段显示
「已暂停」、进度条不动；点「继续」回到「翻译 14/23 段」继续走完。

### 三、队列断点续跑（意外退出后）

**需求**：队列跑一半被系统杀掉 / 崩了，下次打开要问「要不要接着跑」，并且跳过已完成的。

**做法**：
- `refreshFiles()` 开头调 `saveQueueState()`，把 `状态<TAB>路径` 每行一条写进
  `SharedPreferences("queue")`；「处理中」按「待处理」存，避免崩溃后卡在中间态。
- `setQueueRunning(true/false)` 单独管「进行中」标记，只在 `start()` / `finishRun()` 改，
  避免刷新列表时误清。
- 启动时 `promptResumeQueue()` 弹窗：「共 N 个文件，已完成 X 个，还有 Y 个没处理」，
  两个按钮「继续 / 忽略」。

**踩过的坑（关键）**：第一次实现时弹窗里永远显示「已完成 0 个」。原因是 `onCreate` 里
`buildUi()` → `scanInputDir()` → `refreshFiles()` 会先用**新扫出来的 picked**（状态全是
「待处理」）把偏好设置覆盖一遍，等 1.6 秒后弹窗再读，历史「完成」状态早没了。
修法：`onCreate` 最开头把 `files` 和 `running` 抄进内存字段 `resumeFilesRaw` /
`resumeWasRunning`，弹窗只认这份快照。

实测（ja150 已完成 + ja600 处理中被 `am force-stop`）：重开弹窗显示「共 2 个，已完成 1 个，
还有 1 个没处理」；点「继续」后列表里 ja150 保持「完成」、直接跑 ja600（日志「识别 0/30 段」
说明确实只跑第二个）。

### 四、顺带修的两处

- 日志卡片高度：`0 + weight=1` 改成固定 `dp(210)`。文件列表卡片加了「字幕语言 / 输出格式」

  新增 `liveLlamaPid()` 校验 `/proc/<pid>/cmdline` 含 `libllamaserver` 才认。

## 2026-11-11 v1.1.8（第四批：运行状态文案、速度常显、说明滑到底）

### 1. 「运行状态　模型 未启动」会让人以为没在干活（用户 m08131 反馈）

原因：`collectStats()` 原来只有两个分支 —— 能连上 llama `/metrics` 就报 tok/s，
找到 sherpa 进程就报识别进度，**其余一律写「模型 未启动」**。
可是「没有推理进程」恰好发生在三个**正在干活**的时刻：

| 时刻 | 实际在做什么 | 旧文案 |
| --- | --- | --- |
| ffmpeg 提取音频（89 分钟片子约 30 秒） | 转码 1.7 GB wav | 模型 未启动 |
| 批次间隙 sherpa 退出重启（BATCH=6，每 15 秒一次） | 换批继续识别 | 模型 未启动 |
| 翻译服务冷启动（加载 1.1 GB，30~90 秒） | 读模型 | 模型 未启动 |

改法：按 `busy` + `fileProgress` 区间说人话 —— 空闲 / 正在提取音频（ffmpeg）/
正在启动识别模型… / 正在加载翻译模型（约 2 GB，要 30~90 秒）/ 正在生成字幕…。
`STATS_IDLE` 也从「—」改成「空闲」。

### 2. 段速、倍速一会有一会无（用户 m08147）

原因：sherpa 每批结束就退出、下一批再起（这是内存保护的关键，不能改）。
批间那 1~2 秒统计循环进不了「识别分支」，直接跳到 else，速度整段消失；
即使进了分支，两次采样的 `done` 没变时算出的 spm = 0，也被 `if (spm > 0.5)` 吞掉。

**还有一个更严重的数字错误**：旧算法是「相邻两次采样做差」，
但 sherpa 批间退出那 1~2 秒压根采不到，基准不更新；恢复后进度已跳到 +4 段，
时间差却只有 2 秒 → 4 段 / 0.033 分 = **120 段/分、39× 实时**，
比真实值（21~27 段/分、7~9×）虚高 5 倍。
改成 **60 秒滑动窗口**（`asrSamples` 存 `[毫秒, 已完成段数]`，超 60 秒从头部丢弃，
取首尾两点算斜率，跨度不足 15 秒就沿用上次值）后，批间空档被摊平，读数稳定可信。

改法：加 `lastSpm` / `lastAsrDone` / `lastAsrTotal` 三个缓存字段，
把所有「识别 k/N 段（x 段/分 · y× 实时，剩约 z 分）」的拼装收敛到 `segText()`：
spm 太小时沿用 `lastSpm`，没有进程时用缓存读数照常显示。`start()` 里清零。

### 3. 进度卡片放不下（用户 m08164「卡片可以适当变大」）

`运行状态`、`当前动作` 两行原本 `setSingleLine + ellipsize END`，
「识别 76/268 段（21 段/分 · 7.0× 实时，剩约 9 分）　大核2.6-2.6G」直接截掉一半。
改成 `setMaxLines(2)` 自动折行、卡片（WRAP_CONTENT）随之变高；顺带
把频率文案从「大核2.6-2.6G」压成「大核2.6G」（只有变频时才写 2.5~2.6G），字号 11 → 10.5。

### 4. 使用说明必须先看完全文（用户 m08083）

用户原话：「首次使用说明弹出，要完全拉到底，知道了按钮才能按下」。
实现：按钮初始写「往下滑看完才能继续」+ alpha 0.45 + disabled；
`sc.setOnScrollChangeListener` 里判 `sy >= child.height - sc.height - dp(6)` 才解锁（改回「知道了」）；
内容不足一屏时在 `sc.post` 里直接解锁，避免永远点不动。已截图验证两种状态。

### 5. 说明开头「也可以单独选这两个文件」不准确（用户 m08060 / m08110）

单独装 `model.int8.onnx` + `hy.gguf` 只能跑 SenseVoice 单模：
- 融合 / zipformer 模式要 `zipformer-ja/` 的 4 个文件；

文案改成按模式列依赖，不再说「单独选这两个就行」。用户明确否决「可选增强」话术，
所以这段只写依赖关系，不评价优劣。

## 2026-11-11 04:35 实测：NNAPI 是负优化（结论：不用）

### 能不能用：能
- `libsherpaoffline.so`、`libsherpa-onnx-c-api.so` 里都有 `OrtSessionOptionsAppendExecutionProvider_Nnapi`、`Use nnapi`、`Failed to enable NNAPI ... fallback`；`libonnxruntime.so`（1.28.2）带完整 NNAPI EP。
- 真机（Redmi K30 Ultra / 天玑1000+）直接跑 `libsherpaoffline.so ... --provider=nnapi /data/local/tmp/ja30.wav` → rc=0，stderr 只有 `Use nnapi`，**没有 fallback**，转写文本与 CPU 版一致。

### 快不快：慢 5~6 倍
| 模型 | CPU | NNAPI |
|---|---|---|
| zipformer（30 秒音频，2 线程） | 7 s（两次均 7 s） | 36 s / 42 s |
| SenseVoice（同段音频） | 5 s | 24 s |

原因：ORT 的 NNAPI 只接管部分算子，其余回落 CPU，中间还要 CPU↔加速器拷贝，图被切碎后收益被搬运吃掉；CPU 侧 2 线程 ARM NEON int8 本来就快（RTF≈0.076）。**结论：不默认开，也不做开关。**

### 换新机也未必有用
- NNAPI 在 **Android 15 已废弃**（官方 NNAPI Migration Guide：「The Neural Networks API (NNAPI) is deprecated … deprecated in Android 15」，推荐改 TFLite in Play Services / AICore）。
- 天玑9200+/9400+、骁龙7+ Gen3 都有 NNAPI HAL 与 NPU（联发科 APU、高通 Hexagon），但算子覆盖由厂商 HAL 决定，高通最好、联发科较窄；新机多配 Android 15/16。
- 真要吃 NPU：正路是 ORT 的 QNN EP（高通）或联发科 NeuroPilot，需针对模型图改造/量化，工作量大、收益不确定。

## 2026-11-11 05:20 v1.1.8（第六批：软字幕封装 / 字幕名修复 / 防杀说明）

### 1. 字幕文件名带 @ 的根因与修法
- 现象：磁盘上视频叫 `4K2.ComMfcw-052.mp4`（MediaStore `_id=147216`、`_display_name` 同样无 @），
  但 App 生成的却是 `4K2.Com@Mfcw-052.chs.srt`，多一个 `@`，播放器按名匹配失败 → 不自动加载字幕。
- 旧做法：App 自己拼输出全路径（`stem + langSuffix + ".srt"`），stem 来自 Uri 的 displayName，和磁盘真名不一致。
- 修法：App 只传**输出目录**，环境变量 `ASMR_SUFFIX` 传语言后缀；`run.sh` 用 `basename "$IN"` 自己算：
  `BASE=$(basename "$IN")` / `STEM=${BASE%.*}` / `OUT="$OUTDIR/$STEM$SUF.srt"`。
  `ProcessBuilder` 第二参数从 `outSrt.getAbsolutePath()` 改成 `outDir.getAbsolutePath()`。

### 2. 软字幕（mkv 封装）
- 设备 `libffmpeg.so` **没有** `mov_text`/`subrip`/`ass` 编码器 → mp4 装不了字幕轨；有 `srt` 解复用器与 `matroska` 复用器。
- 做法（`run.sh`，在输出格式 case 之前）：
  `ffmpeg -y -hide_banner -loglevel error -i "$IN" -f srt -i "$OUT" -map 0:v? -map 0:a? -map 1:s -c copy -metadata:s:s:0 language=chi "$MKV"`
  `-map 0:v?`/`-map 0:a?` 用可选 map，纯音频文件也能封。
- 成功后 `echo "$IN|$MKV" >> $W/_soft_list`，并**删掉 srt 与 lrc**（用户要求：软字幕就不再单独留字幕文件）。
- App 侧：「字幕封装」两个 pill（外挂字幕 / 软字幕（mkv）），首次开启弹窗说明代价；
  `finishRun()` 调 `promptDeleteSources()` 读 `_soft_list`，弹「删掉原文件？」；`start()` 调 `deleteSoftList()` 清残留。
- 真机验证（89 分钟整片）：`4K2.ComMfcw-052.chs.mkv` = 2,246,465,999 B，ffmpeg 探测 `Duration 01:29:05.40`、
  `#0:0 Video: hevc 1920x1080`、`#0:1(eng) Audio: aac`、`#0:2(chi) Subtitle: subrip`，目录里没有 .chs.srt/.lrc。
- 音频验证（120 秒 wav）：`a120.chs.mkv` 3,855,404 B，`#0:0 Audio: pcm_s16le`、`#0:1(chi) Subtitle: subrip`。
